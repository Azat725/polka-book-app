# Эксплуатация

## Наблюдение

```bash
docker compose ps
docker compose logs --tail=100 api worker beat pdf-sandbox
docker compose exec api python manage.py check --deploy
df -h
docker stats --no-stream
```

Контролируйте свободный диск (предупреждение заранее, до исчерпания), очередь
pending/processing, ошибки обработки, health API, срок TLS и успешность backup.
Логи не должны содержать initData, Authorization, пароли PDF или текст заметок.
Compose ограничивает журналы основных сервисов тремя файлами по 10 МБ.

## Внешняя зашифрованная копия

Укажите в `.env` свой `RESTIC_REPOSITORY`, например S3-совместимое хранилище,
и необходимые ключи. `RESTIC_PASSWORD` сгенерирован отдельно; потеря пароля
делает восстановление невозможным. Не храните единственную копию пароля на VPS.

Первичная подготовка:

```bash
docker compose --profile tools build backup
docker compose --profile tools run --rm --entrypoint restic backup init
```

Запуск из корня проекта:

```bash
sh infra/backup/run-backup.sh
```

Скрипт временно останавливает API/worker/beat, чтобы дамп и файлы согласовались,
делает pg_dump и шифрованную копию, проверяет репозиторий, применяет срок 30 дней
и восстанавливает сервисы через trap даже при ошибке. Во время копии приложение
кратковременно недоступно для изменений. Разместите запуск в ежедневном timer/cron.
Для большой БД увеличьте размер временного `/snapshot` (сейчас 512 МБ).

Цели RPO 24 часа и RTO 4–8 часов подтверждаются только тренировкой восстановления.
Единичное наличие файлов backup не доказывает возможность восстановить систему.

## Восстановление

Выполняйте сначала на отдельном новом сервере/Compose project, не поверх работающей
библиотеки. Восстановите исходный `.env` с секретами и те же версии приложения/БД.

1. Подготовьте Docker, конфигурацию и volumes, запустите init и db.
2. Посмотрите `restic snapshots` через backup service (`--entrypoint restic`).
3. Восстановите выбранный snapshot в отдельный host-каталог, например `/srv/polka-restore`,
   смонтировав его в одноразовый контейнер backup как `/restore`.
4. В snapshot находятся `/snapshot/database.dump` и `/private`. Скопируйте содержимое
   восстановленного private в **новый** private volume, сохранив владельца UID10001.
5. В новую пустую БД выполните pg_restore дампа. Не запускайте сначала setup с
   миграциями в эту БД, иначе таблицы уже будут существовать.
6. Запустите setup и остальные сервисы, проверьте миграции и пользовательский путь.
7. Проверьте выборочно SHA-256 оригиналов, заметки, позиции и корзину.
8. Только после приёмки переключайте DNS/доступ пользователей.

Пример просмотра копий:

```bash
docker compose --profile tools run --rm --entrypoint restic backup snapshots
```

Окончательно удалённая книга может сохраняться в старых backup до их истечения.
При восстановлении старого снимка это необходимо учитывать в политике удаления данных.

Для безопасного восстановления есть отдельный helper. На **новом сервере** после
подготовки `.env` и образов выполните:

```bash
docker compose up -d db
docker compose run --rm --no-deps init
docker compose --profile tools run --rm restore HEX_SNAPSHOT_ID
docker compose up -d --build
```

Дождитесь `db healthy` перед restore. Замените HEX_SNAPSHOT_ID настоящим ID из
`restic snapshots`. Helper откажется перезаписывать непустую БД или private volume;
восстановление дампа выполняется одной транзакцией. Он не очищает старые данные.
При неудавшемся восстановлении используйте новое пустое окружение и выясните ошибку,
не удаляя автоматически оставшиеся файлы. Выполнение на действующей системе не нужно.

## Обновление

Сначала проверьте новую версию на отдельном окружении и прочитайте её миграции.
Сделайте и проверьте backup. Остановите API/worker/beat, обновите исходники,
пересоберите образы, выполните setup и поднимите сервисы. Проверьте health и
реальный пользовательский путь. Зафиксируйте версии используемых образов.

Откат frontend/backend допустим только при совместимости схемы. Для несовместимой
миграции нужен согласованный откат БД и файлов из одной копии; это может потерять
новые изменения после backup. Не откатывайте production-БД вслепую.

## Диагностика

| Симптом | Проверка |
|---|---|
| Не удаётся войти | Правильный бот/токен, время сервера, свежий запуск Mini App; не логируйте initData |
| PDF остаётся processing | Worker/beat, ProcessingJob, доступность spool, sandbox и его ограничения |
| sandbox_failed | Поддержка user namespaces, Docker seccomp, AppArmor/SELinux; проверка Linux-хоста |
| storage_unavailable | Свободное место, активные reservations, незавершённые загрузки |
| После restart пропали файлы | Проверка mounts и Compose project; файлы должны быть в persistent volume |
| PDF не открывается | Обработка завершена, токен действителен, Nginx internal/Range, content types |
| Ошибка 409 | Версия изменилась на другом устройстве; используйте явный выбор/повтор после обновления |
| Нет поиска в книге | Возможно, документ является сканом без текстового слоя |
| Некорректная обложка | Повтор обработки либо замена обложки; проверьте ограничения parser |
| Не звучит перелистывание | Звук включён, был пользовательский жест, WebView разрешил AudioContext |

Нельзя исправлять sandbox_failed включением `privileged`, Docker socket,
глобальным отключением защит или переключением production на local parser.
